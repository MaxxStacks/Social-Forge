# Build SocialEngine around trust and execution

**SocialEngine needs a commerce foundation before it can credibly challenge Graming or Media Mister.** The reviewed repository is a useful storefront prototype with supplier inventory adapters, but its account page is a browser-storage demonstration: it has no authentication, durable order ledger, wallet or payment integration. The requested SocialEngine identity and dominant **#275ddf** remain changes to implement. Existing tests pass, but they do not establish commercial readiness or premium design quality. Competitor research supports a focused platform-and-service search strategy; it does not establish their rankings, traffic or schema implementation. The strongest route forward combines an original retail design, a dependable funded-account journey and verifiable service information. Copying competitor claims or publishing large numbers of thin pages would undermine that position.

## The current prototype passes smoke tests, not launch acceptance

The audit reviewed commit **1d22142c7a898dd89283d4d31412fc41ffa32649** in `MaxxStacks/Social-Forge`. Its native Node HTTP server serves static documents and read-only supplier inventory. Real order submission returns 403. `/account` loads the shared programs document and reads `sf.demo.orders` from localStorage; it cannot authenticate customers or persist purchases across devices. The README explicitly identifies authentication, database orders, payments, supplier submission and refunds as unfinished. These are verified repository findings, distinct from the handoff's future product requirements. ([README](../README.md), [Repository audit](../research_notes/SocialEngine%20competitive%20foundation/repository.md), [Handoff](../docs/CODEX_CONVERSATION_HANDOFF.md))

Baseline verification completed with **15/15 unit tests and 38 browser checks passing**, no browser JavaScript errors and 390-pixel home/discovery layouts without overflow. Desktop and mobile screenshot inspection nevertheless found a generic “made simple” headline, abstract pale category glyphs, excessive vertical space, duplicated footer blocks, remaining purple accents and no obvious desktop Account navigation. These findings explain why behavioral checks alone cannot approve the design. No branding implementation or deployment occurred during this review.

The browser workflow runs on main pushes/manual invocation, while unit CI also runs on pull requests. Railway is documented as connected to main. That combination does **not establish a required predeployment browser gate**; Railway's actual CI-wait configuration still needs inspection. It also does not prove that every historical deployment failure had the same cause. Phase one acceptance should require unit tests, syntax checks for changed JavaScript, route/asset crawling and desktop/mobile browser QA before merge, followed by a staging smoke test and confirmation that production runs the exact accepted SHA. Add meaningful checks for invalid routes, loading/error/empty states, keyboard navigation and broken footer destinations. Establish reviewed screenshot baselines after the redesign rather than preserving today's defects. ([Workflows](../.github/workflows), [Repository audit](../research_notes/SocialEngine%20competitive%20foundation/repository.md))

## A funded dashboard requires accounting before decoration

Phase two should deliver PostgreSQL persistence, secure authentication and a customer dashboard containing **Orders, Add funds, Transactions/receipts, Support and Settings**. Product acceptance means a customer can sign in, fund an account through an approved processor, receive one durable credit, purchase an approved service and inspect an accurate order timeline after a restart. A decorative balance card is insufficient. Browser storage must never authorize balances, ownership or payment completion.

The ledger and fulfillment state machine must handle duplicate payment events, concurrent purchases, supplier timeouts, failed top-ups, refunds and chargebacks. Acceptance tests should prove that replaying a verified webhook cannot double-credit funds, simultaneous purchases cannot overspend, one customer cannot read another's orders, and a retry cannot submit a second supplier purchase. Receipts, support escalation and reconciliation must work before account-credit promotions or affiliate payouts begin. Current code does not provide these capabilities. Commercial activation also depends on supplier, platform and processor eligibility already identified in the handoff; an authenticated supplier listing does not establish permission to sell it. ([Commercialization requirements](../README.md), [Capability audit](../docs/graming-feature-audit.md))

Launch with a narrower approved catalog if necessary. Sixteen networks are a navigation requirement, not proof that every network has reliable inventory. Use platform-specific terms such as followers, subscribers or members, and show actual quantity limits, prices, delivery expectations and refill rules. Disable unavailable categories clearly instead of manufacturing offers to fill a grid.

## SocialEngine needs a coherent identity across the whole journey

Phase three should replace the accumulated style overrides with a deliberate flat design system: **#275ddf as the dominant brand accent**, controlled neutrals, restrained secondary colors, recognizable network SVGs, confident type and compact product merchandising. Preserve the explicit prohibition on gradients. Create an original product page, storefront navigation and dashboard together so the customer sees one product rather than several unrelated templates. On desktop and mobile, platform, service, quantity, total and next action should be immediately clear. Account access should be obvious from every shopping page. ([Design direction](../docs/CODEX_CONVERSATION_HANDOFF.md), [Shopping-journey benchmark](../docs/graming-shopping-journey.md))

Rebrand visible UI, metadata, transactional email, receipts, error states and support content as SocialEngine. Preserve historical handoff records as history, and migrate legacy storage keys deliberately. Treat SocialEngine.cc as a planned domain until ownership and configuration are confirmed. Do not rename the independent GitHub repository or Railway resources merely to change customer-facing identity. Before committing substantial brand collateral, check name availability and conflicts. A domain extension is a business choice; this research establishes no ranking advantage for `.cc`.

Visual acceptance needs explicit criteria: no gradients or stray purple accents, one coherent footer, authentic icons, consistent spacing, accessible contrast/focus states and reviewed screenshots at phone, tablet and desktop sizes. The final judgment should assess whether browsing and buying feel distinctive and understandable, beyond whether controls respond.

## Compete for search intent with stronger evidence

Graming exposes commercial pages for exact combinations such as Instagram followers and TikTok views, alongside price/quantity variants, FAQs and platform guides. Its titles advertise speed, safety and authenticity; those are **observed marketing claims, not independently verified fulfillment properties**. Its FAQ and terms also differ materially: the terms describe artificial/non-organic services, while FAQ language implies guideline-aligned growth. SocialEngine should match useful question coverage while maintaining consistent, supportable disclosures. ([Instagram page](https://graming.com/buy-instagram-followers/), [TikTok views](https://graming.com/buy-tiktok-views/), [FAQ](https://graming.com/faq/), [Terms](https://graming.com/terms-of-use/))

Media Mister exposes broad service families, account/order tools, calculators, educational resources and API access. That breadth makes operational usefulness a competitive requirement. Start a keyword map around platform + service purchase intent, quantity/price, refill/support and reseller needs; prioritize it with measured demand rather than guesses. Build useful original tools and publish real fulfillment statistics only when enough verified data exists. Disclose commercial interest in comparison articles. ([Media Mister](https://www.mediamister.com/), [Comparison disclosure](https://www.mediamister.com/blog/best-sites-to-buy-x-followers/))

Phase four should make public service pages server-rendered, uniquely useful and indexable, with stable URLs, accurate canonicals, sitemap/robots handling, internal links and proper missing-page status codes. The current shared client-rendered documents and unrestricted article slugs need correction. Protect and exclude private account pages from indexing. If existing indexed URLs change, map redirects before switching domains. Implement truthful Organization/WebSite identity, BreadcrumbList and Article markup where appropriate, plus service/offer representations that fit actual content. Never mark demo inventory or invented ratings as real offers. Validate schema syntax and eligible rich-result features separately. ([Repository audit](../research_notes/SocialEngine%20competitive%20foundation/repository.md), [Google structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies))

**SEO, AEO, AIO and GEO do not require four disconnected content factories.** Google says existing SEO fundamentals apply to AI Overviews and AI Mode, with no special AI schema requirement or guaranteed inclusion. Its current documentation updates report FAQ rich results stopped appearing in May 2026, so FAQ markup is not a commercial visibility shortcut. Answer real questions clearly, identify authors and sources, and earn citations through useful original information. Mass-producing pages without added value risks scaled-content abuse. ([AI features](https://developers.google.com/search/docs/appearance/ai-features), [Documentation updates](https://developers.google.com/search/updates), [Generative content guidance](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content))

## Measure the gap before promising leadership

The available search observations establish discoverable competitor content, not controlled Google rankings, search volumes, backlink quality or AI citation rates. Competitor raw schema was not verified. Establish a dated location/device query baseline, Search Console ownership, conversion events and a monitored answer-engine query set before claiming improvement. Evaluate commercial conversion and completed-order reliability alongside visibility; higher traffic to an unreliable checkout is not progress.

The owner should demand ambitious outcomes while rejecting guaranteed rankings and superficial parity. A stronger brand can earn attention, but reliable funding, clear service terms and recoverable orders create the evidence that customers and publishers can trust. The next release should prove that foundation with a small excellent catalog, then expand using observed demand and fulfillment quality.
